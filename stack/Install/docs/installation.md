# Установка стенда Pilot

Стенд ставится из релиза PilotProAdmin одним скриптом `install.ps1`. Он разворачивает веб-админку и сервис миграции, а по выбору — GitLab, мониторинг и Pilot-Server в монолитном режиме для контуров тест, стейдж и прод. Внешние Pilot, GitLab, PostgreSQL и S3 можно подключить вместо своих.

## 1. Как устроена установка

Документ для администратора, который ставит стенд. Правила доступа и требования безопасности описаны в документе [«Безопасность»](security.md), работа без интернета — в [«GitLab без интернета»](gitlab-offline.md). Что лежит в релизе и как устроен установщик изнутри, описано в документе [«Установка и устройство пакета»](../../../docs/installation-package.md).

Всё берётся из [релиза на GitHub](https://github.com/PilotOpenTools/PilotProAdmin/releases/latest):

| Файл | Когда брать |
|----|----|
| `PilotProAdmin-vX.Y.Z-lite.zip` | Обычная установка. Образы админки и миграции установщик скачивает из GHCR |
| `PilotProAdmin-vX.Y.Z-offline.zip` | Нет доступа к GHCR: образы админки и миграции лежат рядом с `install.ps1` |
| `SHA256SUMS.txt`, `SHA256SUMS-CONTAINERS.txt` | Сверка скачанных архивов |

Внутри архива два файла: `install.ps1` и `README.md` (быстрый старт). `install.ps1` содержит весь установочный комплект. При запуске он задаёт вопросы, распаковывает комплект в **папку установки** `PilotProAdmin-install` рядом с собой (или в каталог `-InstallDirectory`) и поднимает выбранные сервисы.

Перед установкой примите три решения:

| **Решение** | **Варианты** |
|----|----|
| Откуда данные | Чистая установка: пустые серверы Pilot или базы из файлов `.dbp`. Перенос стенда: из резервной копии, снятой в админке («Миграция → Подготовить перенос данных») |
| Что ставить на этой машине | Каждый из сервисов (GitLab, статистика, контуры prod / test / stage) ставится здесь, подключается существующим по адресу или откладывается. Админка ставится всегда |
| Есть ли интернет | Есть: Docker скачает недостающие образы. Нет: образы приносят заранее, см. раздел 5 |

## 2. Что нужно на сервере

Установщик работает на Windows (Docker Desktop) и на Linux (Docker Engine). Для серверов, которые работают круглосуточно, особенно для прода, лучше подходит Linux: Docker Desktop запускается только после входа пользователя в Windows, не поддерживает Windows Server и в крупных организациях требует платной подписки.

**Что поддерживается.** Полный CI/CD работает на GitLab: из комплекта или своём. Pilot-Server ставится в монолитном режиме, по одному серверу на контур. Кластерный режим Pilot-Server установщик не разворачивает, но стенд с ним работает: см. [«Кластерный Pilot»](cluster-installation.md) и [перевод контура в кластер](Pilot-Server_cluster.md). Серверным модулям нужен ServerHost 1.2.0 или новее и общий каталог модулей на всех узлах.

- **Docker.** На Windows — Docker Desktop в режиме Linux containers. На Linux — Docker Engine с плагином compose 2.20 или новее и [PowerShell 7](https://learn.microsoft.com/powershell/scripting/install/install-ubuntu) (`pwsh`).
- **Место на диске и память.** Около 10 ГБ под образы и данные и не меньше 10 ГБ под GitLab, дальше объём растёт вместе с репозиториями и артефактами. Память: GitLab требует не меньше 6 ГБ, все сервисы вместе с GitLab на одной машине — не меньше 16 ГБ.
- **Интернет, если образы скачиваются.** Нужен доступ к ghcr.io (админка и миграция), registry.ascon.ru (Pilot-Server, Pilot-myAdmin), registry-1.docker.io, gcr.io (cAdvisor) и registry.gitlab.com (служебный образ runner), напрямую или через прокси. Образы заданий CI берутся ещё и с mcr.microsoft.com, модули PilotOpenTools — с github.com.

**Папка установки — это и есть стенд.** В ней лежат compose, `.env` со всеми паролями и папка данных `data` (`DATA_ROOT`): базы PostgreSQL, базы, лицензии и настройки Pilot, GitLab, данные админки. Распакуйте архив в постоянное место (`D:\PilotProAdmin`, `/opt/pilotproadmin`), а не в «Загрузки», на рабочий стол, во временную или синхронизируемую с облаком папку. После установки папку нельзя удалять, переносить и переименовывать.

### Подготовка Windows

1.  Установите Docker Desktop с WSL2.

2.  Docker Desktop с WSL2 берёт память по настройке WSL: лимит задаётся в файле %UserProfile%\\.wslconfig (раздел \[wsl2\], параметр memory), по умолчанию это примерно половина памяти компьютера. Для GitLab на этой же машине нужно не меньше 6 ГБ, для всех сервисов вместе не меньше 16 ГБ. После правки выполните wsl --shutdown и перезапустите Docker Desktop. Прокси настраивается в Settings / Resources, раздел Proxies.

3.  В Settings / General включите запуск при входе в систему. Пока пользователь не вошёл в Windows, сервисы не работают.

4.  Запускайте установку из PowerShell при запущенном Docker Desktop. Если Windows заблокировала скачанный скрипт, после сверки архива выполните Unblock-File -LiteralPath .\install.ps1.

### Подготовка Linux

Установите Docker, включите его автозапуск и поставьте PowerShell 7. Официальный скрипт Docker подходит для Ubuntu, Debian и RHEL-совместимых систем:

> curl -fsSL https://get.docker.com \| sudo sh
>
> sudo systemctl enable --now docker
>
> docker compose version

На дистрибутивах, которые скрипт не поддерживает, ставьте Docker из репозитория дистрибутива и проверьте версию compose: с версией ниже 2.20 установка не запустится. Docker должен быть локальным (unix-сокет): папки данных монтируются с диска этой машины.

Если нужен прокси, создайте файл /etc/systemd/system/docker.service.d/http-proxy.conf:

> \[Service\]
>
> Environment="HTTP_PROXY=http://proxy:3128" "HTTPS_PROXY=http://proxy:3128" "NO_PROXY=localhost,127.0.0.1"

и примените его: sudo systemctl daemon-reload, затем sudo systemctl restart docker.

### Чем отличаются Windows и Linux

| **Что** | **Windows** | **Linux** |
|----|----|----|
| Запуск установки | .\install.ps1 | sudo pwsh ./install.ps1 (root нужен, чтобы отдать папки данных пользователям контейнеров) |
| Запуск после перезагрузки | После входа пользователя, если включено в настройках Docker Desktop | Сам, через systemd, вход пользователя не нужен |
| Память | Ограничена настройкой WSL2 (файл .wslconfig) | Без ограничения |
| Права на папки данных | Права на DATA_ROOT установка не меняет: закройте доступ средствами Windows. Доступ к .env ограничивается пользователем, SYSTEM и администраторами | Админка и миграция работают под UID 1654, Grafana под 472: установщик сам отдаёт им их каталоги. .env и каталоги с секретами получают права 600 и 700. Данные PostgreSQL принадлежат UID 999, читать их и делать копию нужно через sudo |
| Кто запускает docker | Пользователь Docker Desktop | sudo или группа docker. Участие в группе равносильно правам root |
| Закрытие портов | Брандмауэр Windows | **Правила ufw и firewalld не закрывают опубликованные порты Docker.** Нужна цепочка DOCKER-USER, см. ниже |
| Мониторинг | node-exporter и cAdvisor показывают виртуальную машину WSL, а не сам компьютер. Журнал входов не собирается | Показывают настоящую машину. Promtail читает /var/log/auth.log или /var/log/secure |
| SELinux | Нет | В режиме enforcing контейнеры не получат доступ к папкам, см. ниже |

**Порты на Linux.** Docker добавляет свои правила раньше правил ufw и firewalld, поэтому порт останется открытым, даже если он запрещён в них. Ограничивайте доступ в цепочке DOCKER-USER. Пример: PostgreSQL прода (порт 5433) на интерфейсе eth0 доступен только машине 10.0.0.3. Правила вставляются в начало цепочки, поэтому сначала запрещающее, затем разрешающее:

> sudo iptables -I DOCKER-USER -i eth0 -p tcp -m conntrack --ctorigdstport 5433 --ctdir ORIGINAL -j DROP
>
> sudo iptables -I DOCKER-USER -i eth0 -p tcp -m conntrack --ctorigdstport 5433 --ctdir ORIGINAL -s 10.0.0.3 -j RETURN

Сохраните правила средствами дистрибутива (например, пакетом iptables-persistent) и повторите их для остальных служебных портов: RustFS, миграция, Prometheus, Loki, 9100, 9101. Если в .env задан INTERNAL_BIND, установка пишет в папку установки готовый файл правил firewall-linux.sh (на Windows firewall-windows.ps1) для служебных портов этой машины и ничего не применяет: проверьте его командой sh firewall-linux.sh --test и примените командой sudo sh firewall-linux.sh (Windows: .\firewall-windows.ps1 от администратора). Снять правила можно ключом --remove (-Remove). Правила Linux пропадают после перезагрузки: запускайте файл при старте системы, после Docker.

**HTTPS для админки и Grafana (необязательно).** По умолчанию они работают по HTTP. Чтобы включить HTTPS, положите в папку установки файлы certs/tls.crt и certs/tls.key (PEM, ключ без пароля) и запустите установщик ещё раз: админка и Grafana ответят по HTTPS на тех же портах. Самоподписанный сертификат для закрытой сети:

> openssl req -x509 -newkey rsa:2048 -nodes -days 825 -keyout certs/tls.key -out certs/tls.crt -subj "/CN=pilotproadmin" -addext "subjectAltName=DNS:localhost,DNS:host.docker.internal,IP:10.0.0.3"

В сертификате должны быть имена и адреса, по которым открывают админку и Grafana. После включения HTTPS задайте в .env ADMIN_PUBLIC_URL=https://…, в GitLab (Admin / Applications) смените Redirect URI приложения админки на https://\<админка\>/GitLab/Callback, а в переменных групп модулей задайте ADMIN_URL=https://\<админка\>:5300. Самоподписанный сертификат задания CI не знают: добавьте в переменные группы переменную типа File CURL_CA_BUNDLE (для dotnet ещё и SSL_CERT_FILE) с содержимым tls.crt. GitLab и Pilot-Server установщик на HTTPS не переключает.

**SELinux.** Проверьте режим командой getenforce. При значении Enforcing разметьте папку установки: sudo chcon -Rt container_file_t /opt/pilotproadmin/PilotProAdmin-install. Сервисам мониторинга и runner, которые монтируют docker.sock, /proc, /sys и /var/log хоста, вероятно, понадобится отдельная политика. На такой системе установка не проверялась, решение согласуйте с ИБ.

## 3. Установка на одну машину

Скачайте архив, сверьте его SHA-256 с SHA256SUMS.txt (Get-FileHash на Windows, sha256sum на Linux), распакуйте в постоянную папку и запустите:

> cd D:\PilotProAdmin
>
> .\install.ps1

На Linux:

> cd /opt/pilotproadmin
>
> sudo pwsh ./install.ps1

Ключи запуска:

| **Ключ** | **Что делает** |
|----|----|
| -InstallDirectory \<папка\> | Папка установки вместо PilotProAdmin-install рядом со скриптом. При обновлении указывайте прежнюю |
| -Backup \<каталог\> | Восстановление из резервной копии: каталог с manifest.json |
| -ImageArchive \<файл\> | Архив образов админки и миграции (PilotProAdmin-vX.Y.Z-linux-amd64-images.tar.gz), если он лежит не рядом со скриптом |
| -PilotImage \<образ\> | Свой образ Pilot-Server вместо закреплённого в комплекте |

### Вопросы установщика

1.  **Восстановить из резервной копии?** «Нет» — чистая установка, дальше вопросы ниже. «Да» — см. «Перенос стенда из резервной копии».
2.  **GitLab:** подключить существующий (адрес сервера) или установить здесь. Для нового GitLab установщик спросит имя или IPv4 этой машины: из него собирается адрес GitLab, по которому его открывают браузеры и клоны разработчиков. Не указывайте localhost, если GitLab нужен с других компьютеров.
3.  **Статистика:** подключить Grafana (адрес), установить здесь или позже. Локальная статистика хранит данные в PostgreSQL прода, поэтому без прода на этой машине установщик предложит поставить его или выбрать другой вариант.
4.  **Pilot prod, test, stage:** для каждого контура — подключить существующий сервер (адрес, можно с именем базы), установить здесь или позже.
5.  **База Pilot** для каждого контура, который ставится здесь: пустой сервер или загрузка из файловой базы .dbp, см. ниже.

Если порт занят, установщик предложит свободный: нажмите Enter или укажите свой. В конце он печатает адреса сервисов, путь к .env и готовые значения для общих настроек Pilot (раздел 6). Пароли (Pilot, PostgreSQL, RustFS, Grafana, root GitLab) и ключи (миграции, сборщика статистики, выкладки из CI) установщик создаёт сам, случайными, и записывает в .env папки установки.

Повторный запуск с той же папкой установки вопросов не задаёт: он берёт выбор из .env (ROLES, адреса), распаковывает комплект заново и применяет изменения .env. Так же применяются правки .env, сделанные вручную.

### База из файловой базы Pilot

Пустую базу на PostgreSQL Pilot-Server создать не умеет, поэтому новый сервер ставится без баз. На вопрос «База Pilot \<контур\>» ответьте 2 и укажите папку файловой базы — ту, где лежат base.dbp, base.messages.dbp, base.journal.dbp и папка FileArchive:

> D:\Databases\pilot-ice_ru
>
> D:\Databases\pilot-ice_ru\base.dbp (путь к самому файлу тоже подойдёт)
>
> D:\Databases.zip\Databases\pilot-ice_ru (папка внутри .zip, распаковывать не нужно)

Если в указанном месте несколько баз, установка остановится и перечислит их. Для следующего контура достаточно нажать Enter — подставится тот же путь.

Что делает установка для каждого контура:

1.  Проверяет путь ещё до скачивания образов: в нём должна быть ровно одна база.
2.  Копирует базу во временную папку внутри DATA_ROOT. Исходные файлы не меняются.
3.  Утилитой PostgresMigration из образа Pilot-Server создаёт базу pilot-ice_ru в PostgreSQL контура. При запуске Pilot-Server обновит схему до своей версии.
4.  Выдаёт базе новый идентификатор, чтобы кэши клиентов Pilot для разных контуров не смешивались. Единственным архивом базы становится S3: бакет pilot-ice-ru в RustFS контура. Тела файлов копируются в бакет.
5.  Останавливает Pilot-Server, записывает базу в settings.xml и запускает сервер снова. Прежний файл сохраняется как settings.xml.before-import.

Загрузка выполняется один раз: если база pilot-ice_ru уже подключена, повторный запуск её пропускает. Если база не запустилась, установка предупредит и оставит рабочую копию и прежний settings.xml для разбора. Файловая база должна быть не новее Pilot-Server. Для контуров с внешним PostgreSQL или S3 и при восстановлении из копии загрузка не работает.

Ответ 1 оставляет сервер пустым: базу тогда создают или подключают вручную по документам [«Pilot-Server в Docker на Windows»](Pilot-Server_Docker_Windows.md) или [«на Linux»](Pilot-Server_Docker_Linux.md).

### Перенос стенда из резервной копии

На исходной машине откройте в админке «Миграция → Подготовить перенос данных», скачайте комплект, распакуйте его на машине с Docker Desktop и запустите prepare-transfer.ps1 по инструкции из комплекта. Скрипт напечатает путь к каталогу копии с manifest.json. Перенесите этот каталог на новую машину и запустите:

> .\install.ps1 -Backup 'D:\Backup\2026-11-18_0300' -InstallDirectory 'D:\PilotProAdmin'

Для восстановления выберите новую, пустую папку установки. Установщик ставит на эту машину всё: GitLab, статистику и три контура Pilot с PostgreSQL и RustFS. Версию и редакцию GitLab он берёт из имени архива копии (восстанавливать GitLab можно только в ту же версию). Пароли берутся из копии: они записаны в settings.xml, ролях PostgreSQL и данных RustFS. Установка занимает от 15 до 30 минут, самая долгая часть — GitLab: установщик ждёт его готовности, восстанавливает копию, проверяет число проектов и перезапускает GitLab. Журнал восстановления лежит в DATA_ROOT/gitlab/logs/restore.log.

- **Повторный запуск.** После восстановления появляется метка .installed, поэтому данные повторно не загружаются. Если установка оборвалась после начала восстановления GitLab (метка .restore-started), повторный запуск откажется восстанавливать второй раз: удалите папку установки и тома Docker этой установки и начните заново.
- **Файлы Pilot.** Архивы томов RustFS из копии установщик разворачивает сам до запуска Pilot-Server. Том должен быть пустым: если в нём уже есть данные, установка остановится. Копии времён MinIO (папка minio\\\<контур\>) переносятся в RustFS как есть, адрес S3 в settings.xml меняется на rustfs-\<контур\>.
- **Ключи админки** восстанавливаются, поэтому вошедшие пользователи не разлогиниваются. Мастер первого входа появится снова: введите ключ установки из нового .env.

Если адрес машины изменился, проверьте вручную:

1.  **OAuth-приложение GitLab.** Redirect URI хранится в базе GitLab: Admin / Applications. Укажите там адрес админки с путём /GitLab/Callback и задайте в .env ADMIN_PUBLIC_URL (например, http://10.0.0.5:5300).
2.  **Адреса в CI.** Вебхуки, переменные групп, .gitlab-ci.yml и nuget.config в репозиториях могут содержать старый адрес GitLab или админки.
3.  **Клоны у разработчиков.** Нужны git remote set-url на новый адрес.
4.  **Лицензии Pilot.** Если лицензия привязана к машине, понадобится новая.
5.  **Адреса в общих настройках Pilot** (статистика, GitLab для отчётов), см. раздел 6.

### После чистой установки

1.  **Лицензии Pilot.** Скопируйте файл лицензии в папку контура и перезапустите его сервер: на Windows \<папка установки\>\data\prod\license\Pilot Server\License\\, на Linux \<папка установки\>/data/prod/license/Pilot Server/License/, затем docker restart pilot-server-prod. Для test и stage действия те же.
2.  **Мастер первого входа.** Откройте админку по адресу из вывода установщика, введите ключ установки (ADMIN_SETUP_KEY из .env), войдите через GitLab и проверьте адреса контуров, групп GitLab и Grafana. При загрузке базы из .dbp админка заводит в ней служебного пользователя admin с паролем PILOT_ADMIN_PASSWORD: под ним выкладываются модули и отчёты. Подробнее — в [быстром старте](../../../docs/getting-started.md#ключ-установки).
3.  **Группы GitLab.** Создайте группы для автоматизаций, отчётов, клиентских и серверных модулей и репозиторий типов (см. [README GitLab](../../../gitlab/README.md#группы-и-проекты)) и укажите их в «Настройках» админки. На новом GitLab установщик сам регистрирует runner, создаёт публичный проект проверок pilot-ci/checks, OAuth-приложения и закрывает саморегистрацию. После создания групп модулей запустите установщик ещё раз: шаг GitLab после установки задаст в группах модулей переменные DEPLOY_KEY_TEST (Masked), DEPLOY_KEY_STAGE и DEPLOY_KEY_PROD (Masked и Protected) и защитит ветки main, master, release/\* и dev. Если Docker отдаёт контейнерам негодные адреса DNS (например, из-за Proxifier), до установки задайте в .env RUNNER_DNS=8.8.8.8,1.1.1.1.
4.  **Модули PilotOpenTools.** Откройте в админке страницу «PilotOpenTools» и нажмите «Установить и обновить всё»: на каждый контур встанут PilotClientSdk, PilotReports, PilotLookUp и загрузчик серверных модулей ServerHost из последних релизов GitHub. ServerHost начинает работать после перезапуска сервера Pilot: docker restart pilot-server-\<контур\>. Новые клиентские модули никому не назначены: назначьте их пользователям в Pilot-myAdmin. Без доступа к github.com положите файлы релизов в папку opentools данных админки (\<папка установки\>\data\services\proadmin\opentools), см. [README админки](../../../proadmin/README.md#pilotopentools).
5.  **Общие настройки Pilot и статистика** — раздел 6.

Проверка: на странице «PilotOpenTools» у всех модулей на всех контурах «актуален», на вкладке «Серверные модули» каждый контур показывает версию ServerHost, в клиенте Pilot у назначенного пользователя есть пункты «Модули …» в меню трея, а отчёт строится.

## 4. Несколько машин

Установщик ставит на машине, где его запускают, админку и то, что выбрано «установить здесь». Остальное подключается по адресу. Типовая схема:

| | **Машина 1** | **Машина 2** |
|----|----|----|
| Что ставится установщиком | админка, GitLab, статистика, тест и стейдж | — |
| Что работает | | Прод: Pilot-Server, поставленный штатно по [документации](Pilot-Server_Docker_Linux.md) или существующий |
| Ответ на вопрос «Pilot prod» | подключить существующий: http://10.0.0.1:5546/pilot-ice_ru | |

Установщик из релиза всегда добавляет админку на машину, где его запускают, поэтому разнести по машинам только контуры (прод отдельно, без админки) им нельзя. Контур на другой машине ставят как обычный Pilot-Server и подключают по адресу. Для такого контура настройте вручную:

1.  **Миграцию.** В админке «Миграция → Подключения» задайте адреса PostgreSQL и S3 этого контура, доступные с машины админки.
2.  **Раздел «Серверы».** Он пишет настройки в server-settings контура на диске. Для удалённого контура смонтируйте его папку на машине админки и укажите путь в .env (PROD_ROOT, TEST_ROOT, STAGE_ROOT), затем запустите установщик ещё раз. Без этого правьте настройки сервера в его settings.xml.
3.  **Статистику.** Локальная статистика хранит данные в PostgreSQL прода на машине админки. Если прод на другой машине, подключите внешнюю Grafana или ставьте прод здесь.
4.  **Адрес админки в CI.** В группах модулей GitLab задайте переменную ADMIN_URL=http://\<машина админки\>:5300, а в .env — ADMIN_PUBLIC_URL с тем же адресом.
5.  **Сеть.** Откройте порты из [документа для ИБ](security.md) и закройте остальные служебные порты.

Кластер Pilot-Server на нескольких машинах разворачивается отдельным архивом релиза PilotProAdmin-vX.Y.Z-cluster.tar.gz, см. [«Кластерный Pilot»](cluster-installation.md).

## 5. Установка без интернета

Архив PilotProAdmin-vX.Y.Z-offline.zip приносит только образы админки и миграции. Остальные образы (Pilot-Server, PostgreSQL, RustFS, GitLab и runner, мониторинг) нужно загрузить в Docker целевой машины до запуска установщика. На машине с интернетом выпишите образы из docker-compose.yml комплекта (после первого запуска он лежит в папке установки, в репозитории — stack/Install/docker-compose.yml), затем для каждого:

> docker pull \<образ\>
>
> docker save -o \<имя\>.tar \<образ\>

На целевой машине загрузите каждый файл командой docker load -i \<имя\>.tar и запустите install.ps1 из offline-архива. Образы, которые уже есть в Docker, установщик не скачивает. Сборщики статистики собираются на месте из базовых образов python и .NET: перенесите и их (FROM в Dockerfile папок collectors). Образы заданий CI переносятся так же, см. [«GitLab без интернета»](gitlab-offline.md), шаг 1.

На целевой машине нужно хранилище образов containerd, иначе docker load теряет digest, и compose не находит образы, закреплённые по digest. Включите его до загрузки:

- **Docker Desktop:** Settings / General / Use containerd for pulling and storing images.
- **Linux:** в /etc/docker/daemon.json добавьте {"features": {"containerd-snapshotter": true}} и перезапустите Docker.
- **Проверка:** docker info показывает driver-type: io.containerd.snapshotter.v1.

Модули PilotOpenTools без доступа к GitHub ставятся из папки opentools данных админки (раздел 3, «После чистой установки»). Как подготовить GitLab и рабочие места разработчиков, описано в [«GitLab без интернета»](gitlab-offline.md).

## 6. Настройка после установки

### Общие настройки админки

Вход в админку — через GitLab (в браузере или Personal Access Token с правом api). Первый раз проходит мастер первого входа с ключом установки. Дальше настройки меняются на вкладке «Настройки»; кнопка «Проверить подключения» проверяет серверы и GitLab.

| **Поле** | **Что указать** | **Пример** |
|----|----|----|
| Серверы Pilot: Тест, Прод, Стейдж | Адрес Pilot-Server **с именем базы**. Если контур на этой же машине, можно указать localhost | http://10.0.0.2:5547/pilot-ice_ru, прод на порту 5546, стейдж на порту 5549 |
| Ветка GitLab | Какая ветка соответствует серверу. Контур без ветки доступен только для просмотра | Тест dev, прод main |
| Задача в коммите | Обязателен ли номер задачи в коммите для этого контура | Включено на проде |
| Группа с автоматизациями | Адрес группы GitLab. Из него админка берёт и сервер GitLab для входа. Указывайте адрес, доступный из браузеров пользователей | http://10.0.0.3:8080/automation |
| Группа с отчётами | Пусто отключает вкладку «Отчёты» | http://10.0.0.3:8080/reports |
| Группа с клиентскими модулями | Пусто отключает вкладку «Модули» | http://10.0.0.3:8080/client-modules |
| Группа с серверными модулями | Для выкладки серверных модулей и «Активных работ» | http://10.0.0.3:8080/server-extensions |
| Репозиторий с типами | Один проект GitLab. Пусто оставляет на вкладке «Типы» только сравнение серверов | http://10.0.0.3:8080/pilot-ice/types |
| Job сборки модуля в CI | Имя задания CI, артефакт которого админка выкладывает на серверы | build_module |
| Номер задачи и ссылка на задачу | Регулярное выражение для номера и шаблон ссылки на трекер | KTN-\d+ |
| Code Review | Вливать в dev только после одобрения не автором. Если разработчик один, выключите | |

Настройки хранятся в DATA_ROOT/services/proadmin/settings.json. Значения из .env (PILOT_\*\_URL, \*\_GITLAB_\*\_URL) действуют только при первом запуске.

**Ключи и учётки для выкладки из CI.** Выкладка из CI требует токен задания (X-Job-Token, админка проверяет его в GitLab) и ключ контура (X-Deploy-Key), выведенного из проверенной ветки: dev — test, release/\* — stage, main и master — prod. Ключи и служебные учётки Pilot, под которыми выкладываются модули, задаются в .env папки установки; пустые ключи установщик создаёт сам:

> MODULES_DEPLOY_KEY_TEST, MODULES_DEPLOY_KEY_STAGE, MODULES_DEPLOY_KEY_PROD
>
> MODULES_DEPLOY_\<КОНТУР\>\_LOGIN, MODULES_DEPLOY_\<КОНТУР\>\_PASSWORD

Учётки можно поменять и в «Настройках» админки. Для серверных модулей учётка должна быть администратором базы: ServerHost принимает команды только от администраторов. После правки .env выполните docker compose up -d proadmin в папке установки. В GitLab те же ключи лежат в переменных групп модулей: DEPLOY_KEY_TEST (Masked), DEPLOY_KEY_STAGE и DEPLOY_KEY_PROD (Masked и Protected). На машине с GitLab их вносит установщик, для внешнего GitLab внесите вручную. Ветки main и release/\* должны быть защищены, иначе Protected-ключи не дают защиты. Шаблон CI без X-Job-Token получает 401: обновите .gitlab-ci.yml модулей кнопкой «Обновить CI у всех модулей» на странице «Модули».

### Общие настройки Pilot на каждом сервере

Настройки модулей PilotOpenTools (Pilot.ClientSdk, Reports) хранятся не в модуле и не в .env, а **в базе каждого сервера Pilot**. Установщик их не задаёт: вписывайте их сами **на каждом сервере — prod, test и stage**. Готовые значения установщик печатает в конце.

1.  Войдите в клиент Pilot администратором этого сервера.
2.  Откройте «Сервис / Настройки / Общие настройки».
3.  Заполните разделы из таблицы и нажмите «ОК». Клиенты получают значения без перезапуска.

| **Раздел** | **Модуль** | **Что указать** |
|----|----|----|
| PilotOpenTools отправка статистики | Pilot.ClientSdk (и Reports берёт отсюда адрес статистики) | «Адрес сервиса статистики»: http://10.0.0.3:5310/api/module-events, «API-ключ» — COLLECTOR_API_KEY из .env |
| PilotOpenTools отчёты (GitLab) | Reports 1.6.0 и новее | «Адрес сервера GitLab»: http://10.0.0.3:8080, без пути. «Группа с отчётами»: путь группы, например reports. «Application ID»: REPORTS_GITLAB_OAUTH_CLIENT_ID из .env. Redirect URI оставьте http://127.0.0.1:7890/callback. С версии 1.6.2 там же отмечаются люди, которым показывается меню PilotReport |

Адреса указывайте такие, какие видят рабочие места пользователей, а не localhost.

**OAuth-приложение для отчётов.** На машине с GitLab установщик создаёт его сам («PilotReports (Pilot client)»). Для внешнего GitLab создайте вручную: Admin / Applications / Add new application, Redirect URI http://127.0.0.1:7890/callback, Confidential снят, scope api. Без Application ID пользователи входят личным токеном GitLab.

При переносе из копии общие настройки приходят вместе с базами Pilot: если поменялся адрес GitLab или сборщика статистики, исправьте их на каждом сервере.

### Статистика и мониторинг

Вся статистика попадает в базу pilot_metrics на проде, Grafana читает её оттуда.

| **Источник** | **Где задан адрес** | **Что сделать** |
|----|----|----|
| Клиентские модули и отчёты | Общие настройки Pilot, раздел «PilotOpenTools отправка статистики» | Задать на каждом контуре |
| Серверные модули | METRICS_HOST в .env; пусто — сборщик на этой же машине | Ничего, если статистика на этой машине |
| Автоматизации | Адрес не нужен: сборщик читает лог Pilot-Server | Логирование включено на test и stage, на prod выключено; проверьте на вкладке «Серверы» |

**Ключ сборщика.** Если задан COLLECTOR_API_KEY, события без него отклоняются. Серверные модули получают ключ из .env сами, для клиентских модулей и отчётов укажите его в общих настройках.

**Контур в статистике.** Сборщик определяет контур по адресу сервера Pilot: порт 5549 — stage, 5547 — test, остальное — prod. Если порты другие, поправьте ENV_MAP в .env (формат подстрока=контур;...;\*=контур по умолчанию) и запустите установщик ещё раз.

**Проверка.** С рабочего места Pilot откройте http://10.0.0.3:5310/health. Постройте отчёт и запустите клиентский модуль: в Grafana (порт 3000), папка «CI/CD Pilot», в течение минуты появятся записи с правильным контуром. Если данных нет, смотрите логи Pilot.ClientSdk.log и Reports.log в %AppData%\ASCON\Units Logs\Logs.

### Параметры .env

.env лежит в папке установки. Установщик создаёт его из .env.example комплекта, при повторных запусках сохраняет. После ручной правки запустите установщик ещё раз или выполните docker compose up -d в папке установки.

| **Параметр** | **Что это** |
|----|----|
| DATA_ROOT | Папка данных, по умолчанию data в папке установки |
| ROLES, COMPOSE_PROFILES | Что установлено на машине. Записывает установщик |
| COMPOSE_PROJECT_NAME | Имя проекта compose, установщик задаёт уникальное (pilotproadmin-…); от него зависят имена томов |
| ADMIN_SETUP_KEY | Ключ мастера первого входа |
| PILOT_TEST_URL, PILOT_PROD_URL, PILOT_STAGE_URL, GRAFANA_URL | Адреса для первого запуска админки |
| GITLAB_HOST_IP, GITLAB_HTTP_PORT, GITLAB_SSH_PORT, GITLAB_ROOT_PASSWORD | GitLab этой машины. С localhost GitLab недоступен с других машин |
| GITLAB_OAUTH_CLIENT_ID, \_SECRET, \_REDIRECT_URI | OAuth-приложение для входа в админку через браузер |
| REPORTS_GITLAB_OAUTH_CLIENT_ID | OAuth-приложение для входа из модуля отчётов |
| ADMIN_PUBLIC_URL, ADMIN_TRUST_PROXY, ADMIN_ALLOWED_HOSTS | Адрес админки для браузеров, доверие обратному прокси, допустимые имена хоста |
| MODULES_DEPLOY_KEY_TEST, \_STAGE, \_PROD, MODULES_DEPLOY_\<КОНТУР\>\_LOGIN, \_PASSWORD | Ключи контуров и служебные учётки для выкладки модулей из CI |
| MIGRATION_API_KEY | Ключ между админкой и миграцией |
| COLLECTOR_API_KEY, ENV_MAP, METRICS_HOST | Ключ сборщика статистики, правила определения контура, адрес машины со сборщиком |
| INTERNAL_BIND, ADMIN_HOST | IP для служебных портов (пусто — только 127.0.0.1) и адрес машины админки для правил брандмауэра |
| PROD_ROOT, TEST_ROOT, STAGE_ROOT, SERVER_SETTINGS_ROOT | Папки контуров для миграции и раздела «Серверы», если контур на другой машине; пустой SERVER_SETTINGS_ROOT отключает раздел «Серверы» |
| TLS_CERT_FILE, TLS_KEY_FILE | Пути к сертификату и ключу HTTPS, по умолчанию certs/tls.crt и certs/tls.key |

| \*\_PORT | Порты сервисов |

### Где хранятся пароли

Все пароли и ключи лежат в .env папки установки, доступ к файлу ограничен (на Linux права 600). Не пересылайте файл целиком.

| **Что** | **Логин** | **Пароль** |
|----|----|----|
| Pilot-Server | PILOT_ADMIN_LOGIN | PILOT_ADMIN_PASSWORD |
| Админка | вход через GitLab | — |
| Grafana | GRAFANA_ADMIN_USER | GRAFANA_ADMIN_PASSWORD |
| Консоль RustFS | MINIO_USER | MINIO_PASSWORD |
| PostgreSQL, суперпользователь | postgres | PG_SUPERUSER_PASSWORD |
| PostgreSQL, Pilot | pilotuser | PILOT_PG_PASSWORD |
| PostgreSQL, статистика | metrics_writer, metrics_reader | METRICS_WRITER_PASSWORD, METRICS_READER_PASSWORD |
| GitLab | root | GITLAB_ROOT_PASSWORD, только начальный |

При переносе из копии у контуров могут быть свои пароли с префиксами PROD\_, TEST\_ и STAGE\_: значение с префиксом важнее общего. Имена MINIO_USER и MINIO_PASSWORD исторические: это ключ и секрет доступа RustFS.

> **Смена паролей.** Пароли PostgreSQL и RustFS записываются в базы при первом запуске. Если поменять их только в .env, сервисы перестанут подключаться: меняйте одновременно .env, роль в PostgreSQL (ALTER ROLE), учётную запись RustFS и settings.xml контура. Пароли Pilot, Grafana и GitLab меняются в их интерфейсах, после этого поправьте .env.

Пароли администраторов Pilot и ключи S3 для миграции лежат в DATA_ROOT/services/migration/config.json открытым текстом. На Linux файл создаётся с правами 600; на Windows закройте папку данных средствами ОС.

### Где что лежит

> \<папка установки\>
>
> .env, docker-compose.yml, install-stack.ps1 — комплект, распаковывается при каждом запуске установщика (кроме .env)
>
> monitoring\\, collectors\\, init\\, ci-checks\\ — конфигурация мониторинга, сборщики, init-скрипты, проверки CI
>
> data\\ — DATA_ROOT:
>
> .installed — метка: данные повторно не восстанавливаются
>
> prod\\, test\\, stage\\ — контуры: license\Pilot Server\License\\, pilot-server\settings\settings.xml, databases\\, postgres\\, server-settings\\, logs\\
>
> services\proadmin\\, services\migration\\ — данные админки и миграции
>
> import\\, export\\ — присланные базы и выгрузки
>
> gitlab\\ — GitLab; журнал восстановления gitlab\logs\restore.log

Вне папки установки, на томах Docker проекта compose: файлы Pilot (S3) в RustFS (\<проект\>\_rustfs\_\<контур\>), данные Grafana, Loki и Prometheus, артефакты и загрузки GitLab. Список томов: docker volume ls. Не удаляйте тома и не запускайте docker compose down -v без копии. Копию вместе с томами делает «Миграция → Подготовить перенос данных».

**Файловый архив Pilot (S3)** хранит RustFS (rustfs/rustfs:1.0.5, Apache-2.0): контейнер rustfs-\<контур\>, адрес S3 для Pilot http://rustfs-\<контур\>:9000, бакет pilot-ice-ru. Файлы лежат в именованном томе, а не в папке данных: на Windows папка хоста, подключённая к контейнеру, ломает составную загрузку больших файлов (RustFS отвечает NoSuchKey). RustFS 1.0.x вышел недавно: поведение с Pilot-Server под вашей нагрузкой проверьте на тесте, поддержку хранилищ, отличных от MinIO, уточните у вендора Pilot.

### Обновление

Снимите копию («Миграция → Подготовить перенос данных»), скачайте lite новой версии, распакуйте в любую папку и запустите с прежней папкой установки:

> .\install.ps1 -InstallDirectory 'D:\PilotProAdmin\PilotProAdmin-install'

Установщик сохранит .env и данные, распакует новый комплект и переключит админку и миграцию на образы новой версии. Остальные контейнеры пересоздаются, только если изменились их образы или настройки. Старый распакованный архив после этого можно удалить, папку установки — нет. Обновление Pilot-Server по контурам описано в [README стека](../../README.md#версии-образов).

### Полезные команды

Выполняйте в папке установки. На Linux, если пользователь не входит в группу docker, добавляйте sudo:

> docker compose ps \# что запущено
>
> docker compose logs -f pilot-server-prod \# логи сервиса
>
> docker compose restart proadmin \# перезапуск сервиса
>
> docker compose down \# остановить всё, данные остаются
>
> docker compose up -d \# запустить снова

Ключ первого входа: Select-String -LiteralPath .\\.env -Pattern '^ADMIN_SETUP_KEY=' на Windows, sudo sed -n 's/^ADMIN_SETUP_KEY=//p' .env на Linux.
