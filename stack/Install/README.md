# Стек: установочный комплект

Комплект поднимает стенд Pilot с циклом разработки расширений: контуры prod, test и stage, GitLab с CI, веб-админку и мониторинг. Этот файл написан для разработчиков. Установка, безопасность и работа без интернета описаны в отдельных документах.

Отдельно комплект не передаётся: `scripts/package-release.ps1` кладёт его внутрь `install.ps1` релиза (здесь `install.ps1` становится `install-stack.ps1`), и установщик релиза распаковывает его в папку установки ([«Установка и устройство пакета»](../../docs/installation-package.md)). Код, который читает папки `images/`, `data/` и файлы `IMAGES.txt`, `PASSWORDS.md` рядом со скриптом, остался от прежней передачи комплекта папкой; установщик релиза этим путём не пользуется (образы уже загружены, данные приходят из `-Backup`).

## Что запускается

| Роль машины | Сервисы | Порты |
|---|---|---|
| `prod`, `test`, `stage` | Pilot-Server, PostgreSQL, RustFS (S3-хранилище файлов), Pilot-myAdmin Web | Pilot 5546, 5547, 5549; myAdmin 5601 (на проде всегда), 5602 и 5603 (test и stage) только с ключом `-WithMyAdmin` |
| `admin` | Веб-админка `pilot-proadmin`, сервис миграции `pilot-migration` | 5300 |
| `metrics` | Grafana, Prometheus, Loki, сборщик статистики | Grafana 3000, сборщик 5310 |
| `gitlab` | GitLab CE, GitLab Runner | 8080, ssh 2224 |

Служебные порты PostgreSQL, RustFS, миграции, Prometheus и Loki по умолчанию открыты только на самой машине. Без ключа `-Roles` на машину ставится всё, кроме GitLab: он добавляется ключом `-WithGitLab` или вместе с данными из `data`.

## Внешние сервисы

Git-хостинг, PostgreSQL и S3 можно выбирать независимо. Для внешних сервисов используйте адреса, доступные из контейнеров стенда.

- **GitLab из комплекта.** Добавьте `-WithGitLab` или `--with-gitlab`. Для существующего GitLab оставьте роль `gitlab` выключенной и укажите `GITLAB_GROUP_URL` и нужные адреса групп и репозиториев. Используется CI этого GitLab.
- **GitHub.com.** Оставьте роль `gitlab` выключенной и укажите `GITHUB_TYPES_REPOSITORY=https://github.com/владелец/репозиторий`. Вход в PilotProAdmin выполняется учёткой администратора Pilot. Публикация типов из влитого PR доступна на тестовом контуре. Редактирование и слияние выполняются в GitHub.
- **PostgreSQL.** Для каждого контура отдельно задайте `<КОНТУР>_EXTERNAL_PG_HOST`, при необходимости `..._PORT` и `..._DATABASE` (по умолчанию `5432` и `pilot-ice_ru`), и `<КОНТУР>_PILOT_PG_PASSWORD`. Администратор PostgreSQL заранее создаёт базу и даёт `pilotuser` права владельца. Установщик проверяет вход и пропускает контейнер PostgreSQL этого контура. В Pilot myAdmin подключите эту базу под тем же именем, которое указали в `..._DATABASE`. Если имя изменилось, укажите его также в `PILOT_TEST_URL`, `PILOT_STAGE_URL` или `PILOT_PROD_URL`. Для внешнего PostgreSQL прода при использовании метрик заранее подготовьте `pilot_metrics` и роли `metrics_writer` и `metrics_reader` по образцу `init/postgres/02-metrics-roles.sh`. Для Grafana можно задать `METRICS_PG_SSLMODE`.
- **S3.** Укажите `<КОНТУР>_EXTERNAL_S3_URL`, `<КОНТУР>_EXTERNAL_S3_BUCKET`, `<КОНТУР>_S3_ACCESS_KEY` и `<КОНТУР>_S3_SECRET_KEY`. Установщик проверяет доступ к готовому бакету и пропускает локальный RustFS. При подключении базы в Pilot myAdmin укажите этот же бакет как S3-архив. Для миграции адрес и ключи подставляются из `.env`.

Внешние PostgreSQL и S3 подключаются при чистой установке (`-NoData` / `--no-data`). Резервные копии и восстановление внешней базы и бакета выполняются средствами их владельца. Скопировать данные из прежнего контура можно штатной миграцией после подключения новой базы и архива к Pilot. Проверьте совместимость конкретных версий PostgreSQL и S3 с вашей версией Pilot.

### Публикация типов из GitHub

1. В PilotProAdmin откройте «Типы» и скачайте «Экспорт типов и workflow». Архив содержит текущие метаданные тестового Pilot, `ci/validate.py` и `.github/workflows/pilot-types.yml`.
2. Поместите эти файлы в ваш репозиторий, настройте ветку `dev` и обязательную проверку `validate` для PR. Ограничьте изменения workflow и валидатора правилами репозитория, например через обязательное ревью владельцев.
3. Сделайте правку типов в отдельной ветке, влейте PR в `dev` и дождитесь успешного запуска workflow на коммите слияния. В PilotProAdmin введите номер PR и токен GitHub с доступом к репозиторию и правами чтения Contents, Pull requests и Actions. У аккаунта должны быть права записи в репозиторий. Токен используется для проверки операции и в настройках не сохраняется.
4. Нажмите «Проверить CI и записать на тест». PilotProAdmin принимает только текущий коммит `dev` из влитого PR с успешным запуском `pilot-types.yml` после слияния. Результат появится в «Операциях».

## Пароли, ключи и права

- Первая установка на одну машину: пароли-заглушки из `.env.example` (Pilot, PostgreSQL, RustFS, Grafana, root GitLab) установка заменяет случайными, значения лежат в `.env`, их список печатается в конце. Если машин несколько (заданы `INTERNAL_BIND` или `*_HOST`), заглушки остаются и установка останавливается: пароли нужно задать одинаково на всех машинах. Если роль `gitlab` добавлена к уже установленному стеку, заглушка root GitLab заменяется случайным паролем, пока в `DATA_ROOT/gitlab/data` нет данных; если данные уже есть, `.env` не меняется, установка предупреждает: смените пароль в GitLab и запишите новый в `.env`.
- В `docker-compose.yml` у паролей нет значений по умолчанию: `PG_SUPERUSER_PASSWORD`, `PILOT_PG_PASSWORD`, `METRICS_WRITER_PASSWORD`, `METRICS_READER_PASSWORD`, `MINIO_USER`, `MINIO_PASSWORD` (ключ и секрет доступа RustFS, имена исторические), `GRAFANA_ADMIN_PASSWORD` и `MIGRATION_API_KEY` обязательны (`${X:?…}`), а контур может задать свой пароль префиксом (`PROD_PG_SUPERUSER_PASSWORD` и т. д.), тогда общий не нужен. Compose проверяет их во всём файле, в том числе у сервисов ролей, которых на машине нет, поэтому установщик до запуска compose проверяет `.env` на любом пути (чистая установка, повторный запуск, бэкап, несколько машин). Нет значения, нужного ролям этой машины, - установка останавливается и называет ключ: пароль внутри данных контуров установка не придумывает. Нет значения, которое роли этой машины не нужно (например, пароль Grafana на машине только с `prod`), - установка записывает случайное. Init-скрипт PostgreSQL (`init/postgres/01-pilot.sh`) без `PILOT_PG_PASSWORD` останавливается, роль `pilotuser` с паролем `password` не создаётся.
- Роли PostgreSQL для статистики: `metrics_writer` (владелец базы `pilot_metrics`, под ней пишут сборщики и создают свои таблицы) и `metrics_reader` (Grafana: только `CONNECT`, `USAGE` на схемы и `SELECT` на таблицы, включая будущие). Обе без прав на базы Pilot, у `pilotuser` прав на `pilot_metrics` нет, источник Grafana помечен только для чтения. Пароли - `METRICS_WRITER_PASSWORD` и `METRICS_READER_PASSWORD`: их в данных PostgreSQL нет, установка задаёт их ролям при каждом запуске, поэтому пустые генерирует сама (на одной машине). Несколько машин делят один набор: установка останавливается и просит задать их одинаково на всех машинах.
- Роли и права на `pilot_metrics` на машине с ролью `prod` приводит `init/postgres/02-metrics-roles.sh`: при первом старте на пустой папке его запускает образ postgres, при обновлении существующей установки (база создана по-старому под `pilotuser`) и после восстановления из бэкапа - установщик командой `docker exec postgres-prod bash /docker-entrypoint-initdb.d/02-metrics-roles.sh` (до запуска остальных сервисов и ещё раз после создания баз Pilot). Скрипт идемпотентен: создаёт роли или обновляет пароль, передаёт владение базой и её объектами `metrics_writer` (`REASSIGN OWNED` не применяется: он забрал бы и базы Pilot), выдаёт права `metrics_reader`, отзывает права на `pilot_metrics` у `pilotuser` и `PUBLIC` и закрывает `CONNECT` к базам Pilot (их владелец `pilotuser` заходит как владелец). База Pilot, созданная после запуска скрипта, остаётся доступной для захода (без прав на данные) до следующего запуска установки. Пароли скрипт читает из окружения контейнера (их задаёт compose), в аргументы `docker exec` они не попадают. Закрыть `CONNECT` у ещё не созданной базы нельзя, поэтому после появления новых баз Pilot (в том числе в раскладках `prod` + `metrics` без установщика) запустите ту же команду ещё раз. Передаются схемы, таблицы, последовательности, представления, функции и типы (enum, domain, составные, диапазонные); если у `pilotuser` останется объект другого вида, скрипт заканчивается ошибкой с текстом «остались объекты pilotuser», но права `metrics_reader` к этому моменту уже выданы: передайте объект `metrics_writer` вручную и запустите скрипт снова. Ожидание блокировок ограничено 30 секундами (`lock_timeout`): при долгой транзакции сборщика скрипт завершится ошибкой, а не зависнет. Если `CONNECT` к базам Pilot давала другим ролям именно группа `PUBLIC`, выдайте им право вручную. Поведение прав проверяет на настоящем PostgreSQL `build/selftest/roles-live-selftest.sh` (`docker run --rm -v "<путь к stack>:/stack:ro" postgres:16 bash /stack/build/selftest/roles-live-selftest.sh`).
- Пустые `MIGRATION_API_KEY` и ключи выкладки из CI `MODULES_DEPLOY_KEY_TEST`, `_STAGE`, `_PROD` (на машине `admin`) генерируются: `/dev/urandom` в `install.sh`, `RandomNumberGenerator` в `install.ps1`. `COLLECTOR_API_KEY` генерируется при первой установке на одну машину; в остальных случаях пустое значение сохраняется, и установка предупреждает: сборщик статистики принимает данные без ключа.
- Старый общий `MODULES_DEPLOY_KEY` переносится в `MODULES_DEPLOY_KEY_TEST`, для stage и prod создаются новые. На машине с ролью `gitlab` значения в переменные групп модулей GitLab (`DEPLOY_KEY_TEST` - Masked, `DEPLOY_KEY_STAGE` и `DEPLOY_KEY_PROD` - Masked и Protected) установка записывает сама, шагом GitLab после установки (см. «Установка с данными»), и удаляет старую `DEPLOY_KEY`. Напоминание задать их вручную печатается на машине с ролью `admin` без роли `gitlab` при каждом запуске, а на машине с GitLab только если шаг пропущен (в `.env` нет ключей или в настройках админки нет адресов групп модулей) или не удался.
- Подпись серверных модулей необязательна и установщиком не включается. Если в группе серверных модулей GitLab задать переменную `MODULE_SIGNING_KEY` (закрытый ключ ECDSA P-256), сборка модуля в CI подписывает zip, а ServerHost версии 1.3.0 и новее, получивший открытый ключ (файл `trusted-keys.pem` в `<DATA_ROOT>\<контур>\databases\.server-modules\`), принимает только такие архивы: загрузить в обход CI свой zip или подменить в нём файл нельзя. Без ключей всё работает как раньше. Как выпустить ключи и включить проверку: `server-extensions\ServerHost\README.md`, раздел «Подпись модулей».
- `.env` и `PASSWORDS.md`: на Linux права `600` после любой записи; на Windows доступ ограничивается текущим пользователем, SYSTEM и администраторами. На Linux каталоги с секретами в `DATA_ROOT` (`services/migration`, `services/proadmin`, `gitlab/config`, `gitlab/runner-config`, `<контур>/pilot-server/settings`) закрыты от остальных пользователей. На Windows права на `DATA_ROOT` установка не меняет: ограничьте доступ сами.
- Ключи защиты данных админки (`DATA_ROOT/services/proadmin/keys`) шифруют cookie входа, токены форм и пароли Pilot в памяти текущих сессий; на диске ими ничего не зашифровано (пароли и токены сервисов лежат в `.env` и настройках). Установка при восстановлении из `data` рядом со скриптом папку `keys` не переносит, даже если она там есть: иначе у всех установок из одного комплекта был бы общий ключ, а так админка создаёт свои ключи при первом запуске. Восстановление из бэкапа своей машины (`-FromBackup`, `--from-backup`) ключи возвращает, иначе все вошедшие были бы разлогинены. На Linux папка `keys` закрыта правами `700`; на Windows права на `DATA_ROOT` установка не меняет. Остальное в `data` для каждой установки не пересоздаётся и нужно для восстановления: пароли контуров (`admin/env/*/.env`), `gitlab-secrets.json`, SSH-ключи хоста GitLab и токен runner (`runner-config`). Поэтому комплект с `data` передают как секрет.
- Если `DATA_ROOT/.installed` есть, а `.env` рядом со скриптом нет, установка останавливается: новый `.env` вернул бы заглушки вместо рабочих паролей. Верните `.env` прежней установки.
- Целостность образов (комплект папкой с `images/`): `IMAGES.txt` хранит для каждого образа полный идентификатор `sha256:…` и отпечаток слоёв. После `docker load` установка сверяет с ними каждый загруженный образ: расхождение - ошибка установки с именем образа и файла (скопируйте папку комплекта заново), сервисы не запускаются. Идентификатор зависит от хранилища образов (classic или containerd), поэтому при расхождении идентификатора сверяются слои, и образ принимается, если слои совпали. Слои не включают конфигурацию образа (ENTRYPOINT, env, CMD): если в файле изменена только она, то при другом хранилище образов на хосте это не поймают. Нет `IMAGES.txt` или записи для образа (комплект старого формата, где идентификатор был из 12 символов) - предупреждение, установка продолжается. Образ RustFS в compose закреплён тегом без digest: после `docker load` у образа нет `RepoDigest`, и целостность обеспечивает эта сверка (дайджест индекса `rustfs/rustfs:1.0.5` для сравнения есть в `docker-compose.yml` и `..\build\README.md`). Остальные сторонние образы закреплены digest в `docker-compose.yml`. Сверка защищает от повреждения файла образа и от подмены его слоёв, но не от подмены только конфигурации образа (см. выше) и не от подмены самой папки комплекта вместе с `IMAGES.txt`: у `IMAGES.txt` нет подписи. С `-SkipLoad` / `--skip-load` сверка не выполняется.
- Имя проекта compose задаёт `COMPOSE_PROJECT_NAME` в `.env` (по умолчанию `cicd`): от него зависят имена томов, например `cicd_grafana_data`.

## Установка с данными

- GitLab: установка ждёт настоящей готовности (запущен `puma`, внутри контейнера отвечает `curl http://localhost/-/readiness`), до 30 минут. Затем останавливает `puma` и `sidekiq`, восстанавливает бэкап, проверяет код возврата `gitlab-backup restore` и число проектов в базе (ноль - ошибка установки с ненулевым кодом), останавливает GitLab командой `docker stop -t 600`, запускает и снова ждёт готовности. Сообщение «Готово» печатается после этого. Журнал восстановления: `DATA_ROOT/gitlab/logs/restore.log`; если GitLab сообщил об ошибках схемы, печатается предупреждение.
- Перед `gitlab-backup restore` ставится метка `DATA_ROOT/.restore-started`. Если установка оборвалась после неё, повторный запуск не восстанавливает данные второй раз (изменённые данные были бы затёрты): очистите `DATA_ROOT` и запустите установку снова.
- Данные Grafana из бэкапа не распаковываются поверх существующего тома `<проект>_grafana_data`: установка останавливается с подсказкой.
- Скачивание образов при сетевой ошибке повторяется до трёх раз с паузой.
- Шаг GitLab после установки выполняется на машине с ролью `gitlab` и при восстановлении, и при чистой установке (после ожидания готовности GitLab, при чистой установке это может занять до нескольких минут). Его делает `gitlab-post-restore.rb` через `gitlab-rails runner`: внутри контейнера он создаёт временный токен root, работает через REST API GitLab и в конце отзывает токен. Шаг закрывает саморегистрацию; задаёт переменные групп модулей (см. «Пароли, ключи и права»); в проектах групп модулей защищает ветки: `main` и `master` - push No one, merge Maintainers, `release/*` и `dev` - push и merge Maintainers (архивные проекты пропускаются); в проектах групп модулей и отчётов, где есть CI (файл `.gitlab-ci.yml` или заданный путь к CI), включает «Pipelines must succeed» (merge только после успешного pipeline; проекты без CI не трогает); для групп модулей и отчётов задаёт защиту ветки по умолчанию у новых проектов (push и merge Maintainers, первый push может сделать Developer; «No one» GitLab в этой настройке не принимает, а если настройка запрещена на уровне экземпляра, шаг печатает предупреждение); при `--gitlab-host` заменяет старый адрес GitLab на новый в `nuget.config` (имя файла без учёта регистра, любая глубина) в ветках `dev`, `main`, `master`, `release/*` и `hotfix/*` проектов групп модулей и группы отчётов. В `nuget.config` меняется только адрес в значениях с `/api/v4/`, коммит с `[skip ci]`, защита ветки на время коммита снимается и сразу возвращается. Адреса групп берутся из настроек админки (`DATA_ROOT/services/proadmin/settings.json`, затем снимок бэкапа, затем `MODULES_GITLAB_GROUP_URL`, `SERVER_MODULES_GITLAB_GROUP_URL` и `REPORTS_GITLAB_GROUP_URL` в `.env`). Старый адрес запоминается в `DATA_ROOT/.gitlab-old-host` и удаляется после успешного шага. Шаг идемпотентен. Если проектная переменная с тем же именем перекрывает групповую, он печатает предупреждение. Модули, у которых в `.gitlab-ci.yml` (ветка `dev`, без неё `main` или `master`) остались переменные ключа с прежним префиксом (вида `<префикс>_DEPLOY_KEY_TEST`; `MODULES_DEPLOY_KEY_*` не в счёт) или нет `X-Job-Token`, шаг перечисляет в предупреждении: их выкладка не пройдёт, пока в админке на странице «Модули» не нажать «Обновить CI у всех модулей» и не влить MR в `dev`. Коммит `[skip ci]` в `main` оставляет pipeline «пропущен»: админка при выкладке сама запускает новый pipeline этого коммита. При сбое установка печатает предупреждение и завершается с ненулевым кодом, повторный запуск повторяет шаг. При чистой установке групп из настроек в новом GitLab ещё может не быть: это не сбой, установка печатает напоминание задать ключи вручную, а после создания групп повторный запуск установки задаёт переменные и защиту. Своё значение защиты, в которое входят отдельные пользователи, шаг при пересоздании правила теряет.
- `--gitlab-host` / `-GitLabHost`: Redirect URI OAuth-приложения админки хранится в GitLab (Admin / Applications). Шаг GitLab после установки добавляет в него адрес возврата админки (`GITLAB_OAUTH_REDIRECT_URI`, иначе `ADMIN_PUBLIC_URL` с путём `/GitLab/Callback`), прежние адреса остаются; для этого на машине с GitLab в `.env` должны быть `GITLAB_OAUTH_CLIENT_ID` и один из этих адресов, иначе установка напомнит сделать это вручную. Адрес админки и `external_url` GitLab должны открываться из браузеров пользователей. Старый адрес в `nuget.config` репозиториев заменяет шаг GitLab (см. ниже); остальные места со старым адресом в базе GitLab (например, вебхуки) и клоны у разработчиков установка не меняет.
- Для контуров на других машинах `PILOT_<КОНТУР>_URL` записывается вместе с именем базы (`.../pilot-ice_ru`), как у локальных.
- Миграция работает под UID 1654: на Linux установка выдаёт ему `databases` контуров test и stage и каталоги настроек контуров.
- При заданном `INTERNAL_BIND` установка пишет файл правил брандмауэра для служебных портов, см. «Служебные порты при нескольких машинах».

## Служебные порты при нескольких машинах

Если сервисы стоят на разных машинах, `INTERNAL_BIND` в `.env` открывает на машине служебные порты в сети: PostgreSQL контуров (5433, 5434, 5435), RustFS (9000 и 9001, 9010 и 9011, 9020 и 9021), миграцию (`MIGRATION_PORT`, 5320), Prometheus (9090), Loki (3100), node-exporter (9100) и cAdvisor (9101). Они нужны только другим машинам стенда: админка ходит в базы и RustFS контуров, агенты отправляют логи в Loki. Пароля у Prometheus, Loki и экспортёров нет, поэтому без брандмауэра к ним подключился бы любой компьютер сети. Порты админки, Grafana, Pilot и GitLab к этим не относятся.

Чтобы не писать правила вручную, при заданном `INTERNAL_BIND` установка кладёт в папку комплекта готовый файл правил: `firewall-linux.sh` на Linux, `firewall-windows.ps1` на Windows. Он пускает на служебные порты только адреса из `.env` (`PROD_HOST`, `TEST_HOST`, `STAGE_HOST`, `METRICS_HOST`, `ADMIN_HOST` - адрес машины с админкой, если она другая, `GITLAB_HOST_IP`) и саму машину, остальным закрывает. В начале файла перечислены порты и разрешённые адреса. Установка файл только создаёт и печатает одно предупреждение с путём к нему; сама ничего не применяет. Просмотрите файл и примените, когда будете готовы.

| | Linux | Windows |
|---|---|---|
| Проверить без применения | `sh firewall-linux.sh --test` | разбор файла PowerShell (в начале файла есть команда) |
| Применить, повтор безопасен | `sudo sh firewall-linux.sh` | PowerShell от администратора: `.\firewall-windows.ps1` |
| Снять | `sudo sh firewall-linux.sh --remove` | `.\firewall-windows.ps1 -Remove` |

- В правила входят только IPv4-адреса. Имя хоста в `*_HOST` установка в адрес не превращает (на другой машине имя может указывать на другой адрес): такое значение пропускается с предупреждением, задайте IP. Машина стенда, которой нет в списке, потеряет доступ к этим портам, поэтому проверьте строку «Разрешены адреса».
- Linux: Docker обходит ufw и цепочку `INPUT`, поэтому правила стоят в цепочке `DOCKER-USER` (своя цепочка `INTERNAL` с одним переходом из неё). Правило смотрит на исходный порт соединения до подмены адреса, поэтому закрывается именно опубликованный порт. Соединения контейнеров этой же машины (мосты `br-*` и `docker0`) не режутся; любой интерфейс с именем `br-*` считается мостом Docker, поэтому посторонние мосты так не называйте. Если Docker не управляет iptables (нет цепочки `DOCKER-USER`), файл останавливается с сообщением, ничего не изменив. Правила пропадают после перезагрузки: запускайте файл при старте системы после Docker. IPv6 не охвачен.
- Windows: запрещающее правило Windows Firewall сильнее разрешающего, поэтому запрет строится из диапазонов адресов, оставшихся после вычета разрешённых, `127.0.0.0/8` и `172.16.0.0/12`: это сети Docker и WSL, откуда приходят контейнеры этой машины. Побочный эффект: машины стенда и чужие хосты из диапазона `172.16.0.0/12` этим файлом не блокируются. `INTERNAL_BIND=0.0.0.0` в список разрешённых адресов не попадает.
- Если машин у стенда одна (`INTERNAL_BIND` не задан), порты слушают только `127.0.0.1`, файл не создаётся, а оставшийся от прошлого запуска удаляется.
- Правила Linux проверены на настоящем `iptables` в одноразовом контейнере (`build/selftest/firewall-live-selftest.sh`): трафик через подмену адреса, как у опубликованного порта Docker. Файл Windows проверен разбором PowerShell и самотестом генерации; на живой Windows-машине его действие не проверялось.

## HTTPS (необязательно)

По умолчанию админка и Grafana работают по HTTP: пароль входа и ключи при этом видны в сети тому, кто её слушает. HTTPS шифрует их. Включить его можно без правки файлов: положите в папку комплекта, рядом с `install`, сертификат `certs/tls.crt` и закрытый ключ `certs/tls.key` (PEM, ключ без пароля) и запустите установку. Админка и Grafana начнут отвечать по HTTPS на тех же портах (`ADMIN_PORT`, `GRAFANA_PORT`), HTTP на этих портах перестанет работать. Файлов нет - всё работает по HTTP, как раньше; убрали файлы и запустили установку снова - вернулся HTTP. Другие пути задаются `TLS_CERT_FILE` и `TLS_KEY_FILE` в `.env` (относительные считаются от папки комплекта). HTTPS включается только на машине с ролью `admin` или `metrics`.

Сертификат должен подходить к имени или адресу, по которым открывают админку и Grafana. Самоподписанный (для закрытой сети) делается так, перечислите свои имена и IP в `subjectAltName`:

```bash
mkdir -p certs
openssl req -x509 -newkey rsa:2048 -nodes -days 825 -keyout certs/tls.key -out certs/tls.crt \
  -subj "/CN=cicd" -addext "subjectAltName=DNS:localhost,DNS:host.docker.internal,IP:10.0.0.5"
```

Как это устроено. `docker-compose.tls.yml` - надстройка к `docker-compose.yml`: у админки (Kestrel: `ASPNETCORE_URLS`, `Kestrel__Certificates__Default__Path` и `KeyPath`) и Grafana (`GF_SERVER_PROTOCOL=https`, `GF_SERVER_CERT_FILE`, `GF_SERVER_CERT_KEY`) включается TLS, файлы монтируются только на чтение. Установка подключает её записью `COMPOSE_FILE=docker-compose.yml,docker-compose.tls.yml` и `COMPOSE_PATH_SEPARATOR=,` в `.env` (при своём `COMPOSE_FILE` дописывается с его разделителем) и убирает, когда файлов нет. Поэтому ручные команды `docker compose …` в папке комплекта и повторный запуск установки видят один и тот же набор файлов. Установка копирует файлы в `DATA_ROOT/tls/admin` и `DATA_ROOT/tls/grafana`, контейнеры монтируют копии. На Linux копии получают права `600` для пользователя контейнера (админка 1654, Grafana 472): общий ключ в папке комплекта пришлось бы открывать всем. Если установка запущена не от root и владельца сменить нельзя, ключ становится доступен для чтения всем пользователям машины, установка об этом предупреждает. На Windows копия создаётся заново из байтов (не `Copy-Item`): Docker Desktop показывает контейнеру режим исходного файла, и ключ, созданный в Linux-контейнере или WSL (режим `600`, владелец root), не прочли бы пользователи Grafana и админки (на проверке Grafana и админка из-за этого не запускались); доступ к копии на хосте ограничен, как у `.env`. Новые файлы подхватываются повторным запуском установки. Установка отказывается продолжать, если найден только один из двух файлов, ключ зашифрован паролем или файл не в формате PEM: иначе админка или Grafana не запустились бы, либо остались без HTTPS незаметно. Совпадение ключа и сертификата она не проверяет.

Что изменить при включении HTTPS:

- Адрес админки и Grafana стал `https://…`. В `ADMIN_PUBLIC_URL` (`.env`) укажите `https://…`; установка предупреждает, если там остался `http://`.
- OAuth GitLab: в GitLab (Admin / Applications) измените Redirect URI приложения админки на `https://<админка>/GitLab/Callback` (и `GITLAB_OAUTH_REDIRECT_URI`, если задан).
- CI модулей: в переменных группы GitLab задайте `ADMIN_URL=https://<админка>:<порт>` (по умолчанию в шаблоне `http://host.docker.internal:5300`). Имя в адресе должно быть в сертификате (`host.docker.internal` в примере выше есть).
- Самоподписанный или корпоративный сертификат задания CI не знают, без него проверка админки падает с ошибкой «UntrustedRoot». Добавьте в переменные группы GitLab переменную типа File с содержимым `tls.crt` (или корневого сертификата вашего центра): GitLab положит его в файл и передаст заданию путь. `CURL_CA_BUNDLE` читает `curl` (проверка библиотек и выкладка модулей), `SSL_CERT_FILE` читают и `curl`, и `dotnet`. Проверено в образе SDK из шаблона CI (curl 8.5, .NET 10): оба варианта добавляют сертификат к системным, а не заменяют их, адреса в интернете (nuget.org) по-прежнему открываются; `dotnet` переменную `CURL_CA_BUNDLE` не читает. Переменные группы GitLab при этой проверке не создавались.
- Проверка состояния контейнера админки: в образе нет `curl`, и проверку по TLS без него не сделать, поэтому Kestrel дополнительно слушает HTTP на `127.0.0.1:8081` внутри контейнера (наружу не публикуется) и проверка идёт туда.
- Prometheus и сборщики к Grafana и админке по HTTP не обращаются, дашборды и источники данных менять не нужно.

GitLab и Pilot-Server комплектом не переключаются, только документация:

- GitLab (omnibus): в `GITLAB_OMNIBUS_CONFIG` в `docker-compose.yml` задайте `external_url 'https://<адрес>'`, положите сертификат и ключ в `DATA_ROOT/gitlab/config/ssl/<адрес>.crt` и `.key`, уберите строки `nginx['listen_port'] = 80` и `nginx['listen_https'] = false` и опубликуйте порт 443. Порядок описан в документации GitLab, раздел «Configure HTTPS manually» (`https://docs.gitlab.com/omnibus/settings/ssl/`). После перехода поменяйте адреса GitLab в настройках админки, `config.toml` runner, `nuget.config` и переменных CI. В комплекте это не проверялось.
- Pilot-Server: в образе есть порт HTTPS (в `settings.xml` образа `ServerParamaters HttPort="5545" HttpsPort="5548"`, у `Ascon.Pilot.Daemon` ключи `--httpPort` и `--httpsPort`). Как задаётся сертификат, в образе и в этом репозитории не описано, порт 5548 комплект не публикует: обратитесь к документации Pilot у поставщика.

## Файловый архив Pilot (RustFS)

Файловый архив Pilot (S3) хранит RustFS (образ `rustfs/rustfs:1.0.5`, лицензия Apache-2.0, релиз 1.0 вышел в сентябре 2026). Порты 9000/9001 (prod), 9010/9011 (test), 9020/9021 (stage), бакет `pilot-ice-ru`, S3 по HTTP.

- Контейнер и сервис compose: `rustfs-<контур>`. Адрес в Pilot Admin и в `settings.xml`: `http://rustfs-<контур>:9000`.
- Данные: именованный том Docker `<проект>_rustfs_<контур>` (вне `DATA_ROOT`).
- Пользователь в контейнере: `rustfs`, UID/GID 10001; права на данные настраивать не нужно.
- Клиент для бакета и учёток: `rc` из образа RustFS; образ задаёт `RUSTFS_IMAGE` (по умолчанию `rustfs/rustfs:1.0.5`).
- Переменные `.env`: `MINIO_USER`, `MINIO_PASSWORD`, `<КОНТУР>_MINIO_*`. Имена исторические, значение - ключ и секрет доступа RustFS (идут в `RUSTFS_ACCESS_KEY` и `RUSTFS_SECRET_KEY`).

**Где лежат данные и почему том, а не папка.** Данные RustFS хранятся в именованном томе Docker на всех платформах, `DATA_ROOT` для них не используется. Причина: на Windows (Docker Desktop) папка хоста подключается к контейнеру через сетевую файловую систему (9p), и на ней RustFS не заканчивает составную загрузку больших файлов (в журнале `reliable_rename failed`, клиент получает `NoSuchKey`); на томе Docker тот же образ работал (составная загрузка 120 МБ, контрольная сумма совпала), одиночная загрузка небольших файлов работала и на папке. Том к тому же быстрее и не требует прав: создаваясь, он берёт владельца 10001 у образа, поэтому ни `chown`, ни создание папки не нужны ни установщику, ни вам. Имя тома `<проект>_rustfs_<контур>` (проект из `COMPOSE_PROJECT_NAME`: установщик релиза задаёт уникальное имя `pilotproadmin-…`, в старых установках - `cicd`, то есть `cicd_rustfs_prod` и т. д.). Посмотреть: `docker volume ls`, `docker volume inspect <том>`. Копия `DATA_ROOT` том не содержит: снимайте его копией «Миграция → Подготовить перенос данных» (часть `rustfs` - архив тома) или командой `docker run --rm -v <том>:/v:ro -v <каталог>:/b alpine tar czf /b/rustfs.tgz -C /v .`. Том удаляется вместе с `docker compose down -v` или `docker volume rm`: не делайте этого без копии.

**Восстановление из бэкапа и том.** `install.ps1 -FromBackup` и `install.sh --from-backup` сами восстанавливают файлы RustFS. Для каждого контура этой машины берётся архив `rustfs\rustfs_<контур>.tgz`. Установка проверяет его (`tar tzf`) и распаковывает в том `<проект>_rustfs_<контур>` до запуска Pilot-Server и до создания бакета, поэтому Pilot стартует сразу с базой и файлами. Если в копии нет архива контура, шаг пропускается. Том должен быть пустым (допустимы только служебные `.rustfs` и `.rustfs.sys`): если в нём уже есть данные, установка останавливается с сообщением и ничего не распаковывает. Тогда восстанавливайте в новую папку установки (`install.ps1 -Backup <копия> -InstallDirectory <новая папка>`): у новой установки свой проект compose и свои пустые тома, а прежние тома остаются нетронутыми, пока вы их не удалите. Имена контейнеров (`postgres-prod`, `rustfs-prod`, `pilot-server-prod`, `pilot-proadmin`, `gitlab` и т. д.) в compose фиксированы, поэтому на одном Docker-хосте две установки одновременно не работают. Восстанавливайте на другом хосте или сначала освободите имена: в папке прежней установки выполните `docker compose down` **без** `-v` - контейнеры удаляются, тома и папка данных остаются. Вернуться к прежней установке можно так же: `docker compose down` в новой папке, `docker compose up -d` в прежней. Если контейнер `rustfs-<контур>` уже запущен, на время записи он останавливается, потом его запускает `compose up`. Работает и на Linux без PowerShell: `install.sh` разворачивает архив сам.

Восстанавливайте базу PostgreSQL и файлы RustFS из одной копии по инструкции [«Перенос стенда из резервной копии»](docs/installation.md#перенос-стенда-из-резервной-копии). Она описывает повтор с пустыми томами и сохранение прежней установки для отката. Перед переключением пользователей проверьте, что документы открываются в клиенте Pilot.

**Ограничения.**

- RustFS 1.0.x вышел недавно. Как он работает с Pilot-Server под вашей нагрузкой, проверяйте на своём стенде, сначала на test: совместимость с формой работы Pilot-Server мы не проверяли. Поддержку вендором Pilot хранилищ, отличных от MinIO, нужно уточнить у вендора: мы этого не проверяли.
- Живая проверка (Docker Desktop, WSL2) подтвердила: образ, `rc`, бакеты, учётки и политики, ротацию паролей и составную загрузку на томе. Скрипты установщика (в том числе распаковка тома RustFS из бэкапа) и бэкапа проверены на заглушках docker (`build\selftest`); сохранение владельца 10001 при распаковке от root проверено на образе RustFS. На живом Docker не проверялись: запуск RustFS на восстановленных данных, Pilot-Server поверх RustFS; ветка восстановления RustFS в `install.sh` на Linux-хосте не запускалась.

## Обновление и ограничения

- Обновление из новой папки: `.env` копируется из старой, `DATA_ROOT` остаётся прежним. Контейнеры Pilot-Server и PostgreSQL при переезде в другую папку пересоздаются (в compose относительные пути монтирования `./init`, `./monitoring`, `./wait-for-postgres.sh`): планируйте короткий простой. Остальные контейнеры пересоздаются, только если изменились образы или настройки.
- cAdvisor с 0.54 понимает хранилище образов containerd (по умолчанию в Docker 29): метка `name` и дашборд «Нагрузка контейнеров» работают. Проверено на Docker 29.9 с containerd и cAdvisor 0.60.6; более старый 0.49.1 на таком хранилище метку `name` не отдавал.
- Prometheus запущен без управления по HTTP: перечитать конфигурацию можно командой `docker kill -s SIGHUP prometheus`. Папка `monitoring/prometheus` смонтирована целиком, поэтому правка файла любым редактором видна контейнеру.
- В логах Loki у каждой строки есть метка `host`: `LOG_HOST` из `.env`, иначе `INTERNAL_BIND`, иначе `localhost`. Так одноимённые контейнеры разных машин различаются: `{host="10.0.0.2", container="pilot-server-test"}`.
- Сборщики автоматизаций получают только каталог логов контура (чтение), а не все тома Pilot-Server.
- Артефакты и загрузки GitLab лежат на Docker-томах `<проект>_gitlab_artifacts` и `<проект>_gitlab_uploads`: на папке Windows (NTFS) иначе загрузка отвечает 500. Они входят в бэкап GitLab (`gitlab-backup`), но находятся вне `DATA_ROOT`.
- Полный CI/CD работает через GitLab. GitHub.com поддерживает публикацию типов на тест. Основной установщик ставит Pilot-Server в монолитном режиме. Для разных машин есть [комплект кластера](docs/cluster-installation.md). Действующий кластер подключается по адресу балансировщика. Настройки раздела «Серверы» вступают в силу после перезапуска всех узлов.
- Grafana, Loki, Prometheus и RustFS (файлы Pilot) хранят данные в именованных томах вне `DATA_ROOT`, копия `DATA_ROOT` их не содержит.

## Как менять комплект

1. **Сборка.** Исходники сборщиков и конфиги мониторинга лежат в `..\metrics`. Установщик релиза собирает `scripts/package-release.ps1` (см. [«Установка и устройство пакета»](../../docs/installation-package.md)), самопроверки описаны в `..\build\README.md`.
2. **Запуск.** На машине разработчика `install` здесь не запускайте: совпадут имена контейнеров и порты с рабочим стеком. Конфигурацию можно проверить без запуска:

   ```powershell
   'PG_SUPERUSER_PASSWORD', 'PILOT_PG_PASSWORD', 'MINIO_USER', 'MINIO_PASSWORD', 'GRAFANA_ADMIN_PASSWORD', 'MIGRATION_API_KEY' | ForEach-Object { Set-Item "env:$_" 'x' }
   $env:COMPOSE_PROFILES = 'prod,admin'
   docker compose config --services
   ```

3. **Новый сервис.** Назначьте сервису профиль-роль и добавьте его в документы. Порт, нужный только сервисам, публикуйте через `${INTERNAL_BIND:-127.0.0.1}`.
4. **Сервис на другой машине.** Сервисы обращаются друг к другу по именам контейнеров. Если нужный контейнер находится на другой машине, имя отвечает мост `link-*`, поэтому код и строки подключения менять не нужно.
5. **Версии образов.** Сторонние образы закреплены digest в `docker-compose.yml`, кроме RustFS: он приходит через `docker load` и закреплён тегом. Порядок обновления описан в `..\README.md`.
6. **Документы.** При изменении портов, сервисов или обращений в сеть обновите `docs/installation.md` и `docs/security.md`. Сайт и PDF собираются из этих файлов.
